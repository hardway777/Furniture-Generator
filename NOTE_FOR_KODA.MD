# NOTE_FOR_KODA — как работать с данными генератора

Контракт для движковой стороны. Всё, что ниже, проверено прогоном
`verify_slots.py` на двух моделях, а не выведено из намерений: заголовки
взяты из `Files/export_tables.py`, примеры строк — из реальных артефактов.

---

## 1. Что лежит в артефакте

Каталог, куда пишется `Export FBX & Tables`:

```
<bake>.fbx               сама модель
<bake>.fbm/              текстуры, скопированные экспортёром рядом с файлом
<bake>_doors.csv         двери
<bake>_drawers.csv       ящики: на каком сокете висят и каким мешем собраны
<bake>_drawers.txt       предельное выдвижение ящиков
<bake>_shelves.csv       слоты хранения
```

`<bake>_bake_report.txt` пишется **рядом с .blend**, а не в этот каталог —
на него для импорта опираться не нужно.

---

## 2. Формат файлов

Единый для всех CSV:

| | |
|---|---|
| Кодировка | UTF-8, **без BOM** |
| Окончание строк | CRLF |
| Разделитель CSV | запятая |
| Десятичный разделитель | **точка** |
| Единицы | метры, кроме `MaxVolume` (литры) и колонок, явно названных `мм` |

`_doors.csv`, `_drawers.csv` и `_shelves.csv` — настоящие CSV, рассчитаны на
UE DataTable import. **`_drawers.txt` — не таблица**: человекочитаемый текст
на русском, парсить его как CSV нельзя — и не нужно: всё, что из него
нужно движку, лежит в `_drawers.csv` (см. 3.4).

## 3. Структура таблиц

### 3.1 `_shelves.csv` — слоты хранения

Заголовок дословно, 18 колонок:

```
RowName,Section,Body,Type,DoorSocket,SlotSocket,LocX,LocY,LocZ,ExtX,ExtY,ExtZ,ClearX,ClearY,ClearZ,MaxVolume,MaxItems,Depth
```

`SlotSocket` — новая колонка, **индекс 5**, сразу после `DoorSocket`. Все
остальные стоят ровно на прежних местах, порядок не менялся.

| Колонка | Что это |
|---|---|
| `RowName` | уникальное имя строки, напр. `Base_Sec_01_Carcass_Z01`. Стабильно между перезапеканиями |
| `Section` | секция, напр. `Base_04` — то же имя, что у секции в рабочей модели |
| `Body` | меш-владелец отсека: `SM_<bake>_Body` или `SM_<bake>_UpperBody` |
| `Type` | `closed` \| `open` \| `rod` \| `counter` \| `drawer` |
| `DoorSocket` | какое **открытие** ведёт в отсек. Пусто — ничем не закрыт |
| `SlotSocket` | где размещается объект **внутри** отсека. Пустых нет. Для `drawer` — сокет **на меше ящика**, не на `Body` |
| `LocX/Y/Z` | центр короба, метры, в системе координат `Body` |
| `ExtX/Y/Z` | габариты короба целиком, метры |
| `ClearX/Y/Z` | повторяет `Ext` — считать отдельно не нужно |
| `MaxVolume` | тот же короб в литрах |
| `MaxItems` | грубая справка: `1` у `rod`, `0` в остальных случаях |
| `Depth` | **только** у `Type=drawer`, метры. То же число, что в `_drawers.txt` |

Пример строки (модель `full_l_kitchen`, бейк `SLOTSLOT`):

```
Base_Sec_01_Carcass_Z02,Base_01,SM_SLOTSLOT_Body,drawer,SOCKET_Drawer01_01,SOCKET_DrawerCol01_01,-1.8863,-0.3230,0.7275,0.1963,0.5540,0.1100,0.1963,0.5540,0.1100,11.965,0,0.5720
Base_Sec_01_Carcass_Z01,Base_01,SM_SLOTSLOT_Body,open,,SOCKET_Base_Sec_01_Carcass_Z01_08,-1.6205,-0.3090,0.3700,0.7640,0.5820,0.5040,0.7640,0.5820,0.5040,224.103,0,
```

Обрати внимание: у `drawer` две **разные** ячейки — `DoorSocket` это монтажный
сокет ящика (`SOCKET_Drawer01_01`), а `SlotSocket` — сокет коллизии отсека
(`SOCKET_DrawerCol01_01`), и он висит на меше ящика, а не на `Body`. У `open`
`DoorSocket` пуст, `SlotSocket` — сокет отсека на `Body`, `Depth` пуста.

Все три ящика `full_l_kitchen` показывают один и тот же `SlotSocket`: они
дедуплицированы в один меш, у него один центр отсека. Различаются они по
`DoorSocket` — по своему монтажному сокету.

### 3.2 `_doors.csv` — двери

Заголовок дословно, 13 колонок:

```
RowName,Source,Body,Socket,Mesh,Hinge,Width,Height,Thickness,SocketX,SocketY,SocketZ,SocketYawDeg
```

| Колонка | Что это |
|---|---|
| `RowName` | **всегда равна `Socket`** — для UE DataTable имя строки = имя сокета, уникально в пределах файла |
| `Source` | имя объекта-источника в рабочей сцене, для трассировки |
| `Body` | меш, на котором висит сокет |
| `Socket` | имя сокета, join-key для `_shelves.DoorSocket` |
| `Mesh` | уникальный меш этой двери, который сокет обслуживает |
| `Hinge` | `Left` \| `Right` |
| `Width` / `Height` / `Thickness` | габариты фасада, метры |
| `SocketX/Y/Z` | трансформ сокета, пересчитанный в систему `Body` |
| `SocketYawDeg` | его yaw, градусы (на повёрнутых секциях L-кухни это `-90.00`) |

Пример строки:

```
SOCKET_Door03_06,SM_DEBUG_Base_Sec_04_DoorL_01,SM_SLOTSLOT_Body,SOCKET_Door03_06,SM_SLOTSLOT_Door_03,Left,0.2963,0.7150,0.0180,-0.6180,-0.6205,0.4600,-90.00
```

### 3.3 `_drawers.txt` — предельное выдвижение

**Это не таблица.** Русский текст, структура фиксированная:

```
Предельное выдвижение ящико́в: <bake>
<пустая строка>
Выдвижение ограничено коробом: <пояснение, 3 строки>
<пустая строка>
Ящиков: <N>
  <Source>  (сокет <Socket>, меш <Mesh>, корпус <Body>)
      фасад <W> x <H> мм, короб глубиной <D> мм
      максимальное выдвижение: <T> м (<T*1000> мм)
  ...блок на каждый ящик...
```

Реальный блок:

```
  SM_DEBUG_Base_Sec_01_Drawer_01  (сокет SOCKET_Drawer01_01, меш SM_SLOTSLOT_Drawer_01, корпус SM_SLOTSLOT_Body)
      фасад 263 x 175 мм, короб глубиной 572 мм
      максимальное выдвижение: 0.572 м (572 мм)
```

Монтажный сокет и «максимальное выдвижение» есть и в `_shelves.csv`: это
`DoorSocket` и `Depth` строк `Type=drawer`. Меша там **нет** — он лежит в
`_drawers.csv` (см. 3.4). TXT остался для человека и для сверки, парсить его
движку не нужно.

Меш ящика ключевен и для имен: он же владелец в `SlotSocket` этой строки
(`SM_SLOTSLOT_Drawer_01` → `SOCKET_DrawerCol01_01`).

### 3.4 `_drawers.csv` — ящики для движка

Заголовок дословно, 8 колонок:

| колонка | что |
|---|---|
| `RowName` | всегда равен `Socket` — как в `_doors.csv`, чтобы строка годилась для DataTable |
| `Source` | объект в рабочей модели (`SM_DEBUG_...`); только для трассировки |
| `Body` | меш корпуса, на котором висит сокет |
| `Socket` | монтажный сокет ящика — **join-key** из `_shelves.csv.DoorSocket` |
| `Mesh` | меш, из которого собирается компонент ящика |
| `Width`, `Height` | фасад, метры |
| `Depth` | предельное выдвижение, метры; **то же число**, что `Depth` в `_shelves.csv` |

Первые пять колонок совпадают с `_doors.csv` по смыслу и порядку, поэтому обе
таблицы читаются одинаково: строка = подвижная часть, `Socket` её крепит,
`Mesh` — из чего её собрать.

**Строк столько, сколько ящиков-инстансов, а не сколько уникальных мешей.**
Три одинаковых ящика full_l — это три строки с одним `Mesh`:

```
RowName,Source,Body,Socket,Mesh,Width,Height,Depth
SOCKET_Drawer01_01,SM_DEBUG_Base_Sec_01_Drawer_01,SM_SLOTSLOT_Body,SOCKET_Drawer01_01,SM_SLOTSLOT_Drawer_01,0.2633,0.1750,0.5720
SOCKET_Drawer01_02,SM_DEBUG_Base_Sec_01_Drawer_02,SM_SLOTSLOT_Body,SOCKET_Drawer01_02,SM_SLOTSLOT_Drawer_01,0.2633,0.1750,0.5720
SOCKET_Drawer01_03,SM_DEBUG_Base_Sec_01_Drawer_03,SM_SLOTSLOT_Body,SOCKET_Drawer01_03,SM_SLOTSLOT_Drawer_01,0.2633,0.1750,0.5720
```

Это и есть машинная форма «один ассет — N инстансов»: ассет один, строк —
по числу ящиков, и каждая знает свой сокет.

## 4. Соглашение по сокетам

Это ядро контракта. Пять пунктов.

### 4.1 Имя

Имя сокета — это ровно строка из колонки `SlotSocket` или `DoorSocket`,
**без всякой трансформации**. Генератор кладёт в ячейку то же самое имя,
которое стоит на EMPTY в FBX:

```
SOCKET_<что-то>_<NN>
```

* всегда начинается с `SOCKET_`;
* всегда заканчивается на `_NN` — две цифры;
* середина свободная, её никто не парсит.

Важная тонкость по префиксу: **таблицы содержат полное имя вместе с
`SOCKET_`**. Если на стороне UE сокет регистрируется уже без префикса
(`SocketName == SM_...`), то срезать `SOCKET_` надо и со значения ячейки —
это одна и та же операция с обеих сторон. Сверять «имя из FBX» и «значение в
таблице» нужно в одном виде, иначе join молча не найдёт ничего.

### 4.2 Кому принадлежит

Середина имени отвечает на вопрос **«для кого этот сокет»**, а не «чей он по
родителю». Чей — определяет иерархия в сцене, имя же дублировало бы её без
пользы. Четыре вида владельца:

```
SOCKET_Door<NN>        для уникального меша двери SM_<bake>_Door_<NN>
SOCKET_Drawer<NN>      для уникального меша ящика SM_<bake>_Drawer_<NN>
SOCKET_DrawerCol<NN>   для компонента-коллизии того же меша ящика
SOCKET_<RowName>       для самого отсека
```

`<NN>` владельца — это индекс меша, а последний `_NN` в имени — счётчик
сокета (см. ниже). Реальные примеры (`full_l_kitchen`, бейк `SLOTSLOT`):

```
SM_SLOTSLOT_Body:
  ящики (монтаж)      SOCKET_Drawer01_01   SOCKET_Drawer01_02   SOCKET_Drawer01_03
  двери (петля)        SOCKET_Door01_04     ...                  SOCKET_Door04_07
  отсеки               SOCKET_Base_Sec_01_Carcass_Z01_08
                       SOCKET_Base_Sec_04_Carcass_Z01_13

SM_SLOTSLOT_UpperBody:
  двери                SOCKET_Door05_01     ...                  SOCKET_Door09_05
  отсеки               SOCKET_Upper_Sec_04_Carcass_Z01_09

SM_SLOTSLOT_Drawer_01:
  коллизия отсека      SOCKET_DrawerCol01_01
```

Одинаковые ящики дедуплицируются в **один** меш, поэтому у `SM_..._Body`
три монтажных сокета с владельцем `Drawer01`, а не `Drawer01/02/03`: владелец —
меш, а инстансы различаются последним счётчиком (`_01`, `_02`, `_03`).

Владельца можно вывести прямо из имени меша: срезать `SM_<bake>_` и убрать
подчёркивание. `SM_SLOTSLOT_Door_03` → `Door03`, `SM_SLOTSLOT_Drawer_01` →
`Drawer01`, `SM_SLOTSLOT_Drawer_01` → `DrawerCol01` для коллизии. Колонка
`Mesh` в `_doors.csv` отдаёт этот меш напрямую.

**Владелец и родитель — разные вопросы.** `SOCKET_Door03_06` висит на
`SM_SLOTSLOT_Body`, потому что петля принадлежит корпусу; а
`SOCKET_DrawerCol01_01` висит на `SM_SLOTSLOT_Drawer_01`, потому что коллизия
должна выезжать вместе с ящиком.

`NN` — **один счётчик на родительский меш**, а не на строку. Двери и ящики
нумеруются первыми, отсеки продолжают тот же ряд. Реальные диапазоны в
`full_l_kitchen`:

| Меш | монтаж и петли | отсеки | всего |
|---|---|---|---|
| `SM_..._Body` | `01..07` (3 ящика + 4 двери) | `08..15` | 15 |
| `SM_..._UpperBody` | `01..05` | `06..10` | 10 |
| `SM_..._Drawer_01` | — | `01` (`DrawerCol`) | 1 |

У `bedside_dresser` один меш: `01..02` — ящики, `03..04` — отсеки.

Счётчик начинается заново **на каждом меше**, но никогда — на каждой строке.
Пересечение двух номеров внутри одного меша — падение теста, а не
допустимое состояние.

### 4.3 Иерархия — главное правило

Сокет — это **ребёнок меша**, а не сосед. `FindMeshSockets` в
`FbxStaticMeshImport.cpp` обходит поддерево самого меша: sibling-empty
отбрасывается **молча**, без предупреждения, и файл при этом выглядит
абсолютно нормально.

Следствие — ключ поиска парный, но **не всегда `(Body) + (SlotSocket)`**:

| Тип строки | на каком меше ищут `SlotSocket` |
|---|---|
| `closed` / `open` / `rod` / `counter` | меш из колонки `Body` |
| `drawer` | **меш ящика**, не `Body` |
| любая — `DoorSocket` | меш из колонки `Body` |

У `drawer` меш ящика в `_shelves.csv` не указан. Он в `_drawers.csv`
(см. 3.4): `DoorSocket` строки → колонка `Socket` → колонка `Mesh`. Это
единственное место, откуда его берут, и парсить ради него ничего не нужно.

Выводить меш из имени сокета (`SOCKET_DrawerCol01_01` → владелец `Drawer01`
→ `SM_<bake>_Drawer_01`) можно, но не стоит: имя несёт только факт «для
кого», и раскладывать его на части — парсинг, на который контракт не
рассчитан (см. 4.2, там же про `DoorSocket` как про счётчик, не как про
личность).

Искать сокет по имени по всему FBX нельзя: имя уникально только **внутри**
своего меша. Раньше в этом не было нужды, потому что все имена несли префикс
корпуса; теперь владелец говорит «для кого», а «где лежит» даёт только
иерархия.

Порядок работы на стороне UE:

1. импортируешь `<bake>.fbx`;
2. сокеты сами приезжают в `UStaticMeshSocket` на своём меше;
3. для обычного отсека берёшь `SlotSocket` с меша из `Body`;
4. для `drawer` — `DoorSocket` с меша из `Body` (монтаж ящика), а `SlotSocket`
   с меша ящика (коллизия отсека, выезжает вместе с ним);
5. сам меш ящика для компонента берёшь из `_drawers.csv`: `DoorSocket` строки
   → `Socket` → `Mesh`.

Отдельного JSON-sidecard и арматуры нет.

### 4.4 Что вешать на какой сокет

| `Type` | `SlotSocket` указывает на | Что вешать |
|---|---|---|
| `closed` / `open` / `rod` / `counter` | compartment-сокет этой строки, ребёнок `Body` | предмет внутри отсека |
| `drawer` | `SOCKET_DrawerCol<NN>_01`, ребёнок **меша ящика** | компонент-коллизия отсека ящика |

У `drawer` это ровно тот сокет, которого не хватало: коллизия должна
сопровождать ящик, когда тот выезжает, а монтажный сокет
(`DoorSocket`, `SOCKET_Drawer01_01`) остаётся на корпусе — на нём держится
само выдвижение. Два разных вопроса, два разных сокета, и путать их нельзя.

Механика такой коллизии простая: это не физика, а overlap-триггер. Предмет
пересёк объём отсека — значит, он внутри и его надо положить в ячейку
инвентаря. Поэтому объём и центр важнее пивот-точки.

`DoorSocket` и `SlotSocket` отвечают на **разные** вопросы:

* `DoorSocket` — какое открывающееся ведёт в отсек (join-key к `_doors.csv`,
  а у `drawer` — монтажный сокет ящика);
* `SlotSocket` — где стоять предмету, стоящему **в** отсеке.

Пустой `DoorSocket` = отсек ничем не закрыт: открытая ниша, столешница,
штанга. Пустой `SlotSocket` на экспортированной строке — аномалия, такого не
бывает.

Все три ящика одной модели дают одно и то же `SlotSocket`: меш у них общий.
Уникальность строки обеспечивает `DoorSocket`, а не `SlotSocket`.

### 4.5 Трансформ

* Сокет compartment-отсека стоит **ровно** на `LocX/Y/Z` строки — проверено
  раунд-трипом FBX, допуск 1e-3 м.
* Его yaw — это поворот секции, в которой стоит отсек. На L-кухне повёрнутые
  секции дают `-90°`:

  ```
  Base_Sec_04_Carcass_Z01   SOCKET_Base_Sec_04_Carcass_Z01_13    -90.00°
  Base_Sec_05_Carcass_Z01   SOCKET_Base_Sec_05_Carcass_Z01_15    -90.00°
  Upper_Sec_04_Carcass_Z01  SOCKET_Upper_Sec_04_Carcass_Z01_09   -90.00°
  Upper_Sec_06_Carcass_Z01  SOCKET_Upper_Sec_06_Carcass_Z01_10   -90.00°
  ```

  Предмет, посаженный на такой сокет с нулевым трансформом, встаёт лицом
  туда, куда открыта секция.
* **У `drawer` сокет живёт в кадре меша ящика.** Его мировая позиция в FBX не
  равна `Loc*`, потому что меш ящика экспортируется в мировом нуле. Смысл
  позиции раскрывается только при закрытом ящике:

  ```
  монтажный сокет  ×  позиция SlotSocket  ==  LocX/Y/Z     (допуск 1e-3 м)
  ```

  Это и есть проверка, что точка стоит в центре пространства ящика, а не
  где попало. В локальном кадре меша смещение постоянно для одной модели —
  `full_l_kitchen`: `(0, 0.2950, -0.0025)`, `bedside_dresser`:
  `(0, 0.2450, -0.0025)` — центр короба, глубина делённая пополам.
* **У `drawer` есть второй сокет, и он другой.** Монтажный
  (`SOCKET_Drawer01_01`, колонка `DoorSocket`) стоит на фронтальной
  пивот-точке корпуса — на нём держится всё выдвижение, переставлять его
  нельзя. Перемещать его не нужно и не следует: `Loc*` берутся из строки, а
  коллизия висит на своём сокете в центре.

## 5. Связка таблиц

```
_shelves.csv  SlotSocket  -->  UStaticMeshSocket на меше из Body   (отсек)
_shelves.csv  SlotSocket  -->  UStaticMeshSocket на меше ЯЩИКА      (только Type=drawer)
_shelves.csv  DoorSocket  -->  _doors.csv.Socket                   (какое открытие)
_shelves.csv  DoorSocket  -->  _drawers.csv.Socket                 (только Type=drawer)
_shelves.csv  Depth       ==   _drawers.csv.Depth                  (то же число)
_drawers.csv  Socket      ==   RowName этой же строки
_doors.csv    Socket      ==   RowName этой же строки
```

Последняя строка — тот же приём, что у дверей: обе подвижные части читаются
одинаково. `_drawers.txt` в схему не входит — это человек, а не источник
данных (см. 3.3).

Полная иерархия, которую выстраивает движок:

```
меш гарнитура            SM_<bake>_Body                      мировой ноль
└─ сокет крепления ящика SOCKET_Drawer01_01                  позиция ящика
   └─ меш ящика          SM_<bake>_Drawer_01                 относительный ноль
      └─ сокет коллизии  SOCKET_DrawerCol01_01               центр пространства ящика
         └─ компонент    (UE)                                 относительный ноль
```

Узлы 1–2 есть в FBX как есть, узел 4 добавлен этим изменением. Узел 3
движок собирает сам. Правило, согласованное с UE-стороной (блок **A2** в
`AGENT_CONV.MD`), — их формулировка, взятая дословно:

> Каждый блок `_drawers.txt` = один компонент ящика. Сет на компонент — меш
> из поля «меш»; компонент цепляется к сокету из поля «сокет»; имя
> компонента — `RowName` соответствующей строки `_shelves.csv`. Блоков может
> быть N при одном и том же меше: это один ассет и N инстансов, дедуп
> сохраняется на уровне ассета.

Правило сформулировано до того, как появился `_drawers.csv` (блок **Q6**),
поэтому источник для машины теперь другой, а само правило не изменилось:
«поле меш» → колонка `Mesh`, «поле сокет» → колонка `Socket`, имя
компонента → `RowName` той же строки `_shelves.csv`. Читать это из TXT
больше не нужно и не следует.

Сделать узел 3 буквально в FBX нельзя: одинаковые ящики дедуплицированы в
один меш при трёх монтажных сокетах, поэтому в файле один
`SM_<bake>_Drawer_01`, лежащий корнем, а не три.

Для не-ящихничного отсека иерархия короче: компонент висит сразу на меше
гарнитуры, на `SOCKET_<RowName>_NN`.

* `DoorSocket` и `SlotSocket` у `drawer` — **разные** сокеты: монтажный и
  коллизионный. Раньше совпадали, теперь это два узла иерархии.
* `Loc*` уже пересчитаны в систему координат `Body`, как и `SocketX/Y/Z` в
  `_doors.csv` — обе таблицы сходятся в одном пространстве, их можно джойнить
  по `Body`.
* Имена сокетов изменились (см. §4.2), поэтому `_doors.csv`, `_drawers.txt` и
  mesh-секция отчёта теперь отличаются от прежнего снимка **только** именами
  сокетов. Так их и проверяет тест: всё остальное замаскировано и сверяется
  побайтово.

## 6. Контрольные количества

Можно сверить импорт с тем, что реально отправлено:

| Модель | дверей | ящиков | отсеков | строк в `_shelves.csv` | сокетов в FBX |
|---|---|---|---|---|---|
| `bedside_dresser` | 0 | 2 | 2 | 4 | 5 |
| `full_l_kitchen` | 9 | 3 | 13 | 16 | 26 |

Формула: `сокетов = дверей + строк + уникальных мешей ящиков`. Первое слагаемое
— петли дверей, второе — монтажные сокеты ящиков плюс сокеты отсеков, третье —
сокеты коллизии, по одному на меш ящика (у `full_l_kitchen` все три ящика
дедуплицированы в `SM_..._Drawer_01`, поэтому одно слагаемое, а не три).

У `full_l_kitchen` распределение: `SM_..._Body` — 15, `SM_..._UpperBody` — 10,
`SM_..._Drawer_01` — 1.

Строк в `_shelves.csv` = `отсеков + ящиков` (ящик — это тоже строка), поэтому
`16 = 13 + 3`, а по сокетам `26 = 9 + 16 + 1`. Строк в `_drawers.csv` =
числу ящиков: `2` у `bedside_dresser`, `3` у `full_l_kitchen`.

## 7. Ловушки

* Пустой `DoorSocket` — норма для `open` / `counter` / `rod`. Пустой
  `SlotSocket` — **аномалия**, экспортированной строки без сокета не бывает.
* Сокет существует, только если его имя стоит в `SlotSocket` или `DoorSocket`.
  Отдельного перечня сокетов в таблицах нет — FBX сам по себе не источник
  правды о том, что значимо.
* **Не ищи `SlotSocket` строки `drawer` на меше из `Body`** — там его нет, он
  висит на меше ящика. Единственный случай, когда колонка `Body` не ведёт к
  искомому сокету.
* `_drawers.txt` не парсится как CSV: там русский текст, табуляция отступами
  и скобки. Парсить его и не нужно — машина берёт те же поля из
  `_drawers.csv` (см. 3.4), TXT остался для человека.
* **`_drawers.csv` содержит строк столько, сколько ящиков, а не сколько
  уникальных мешей.** У `full_l_kitchen` это три строки с одним и тем же
  `Mesh` — ожидать одну строку на меш значит не понять, ради чего файл
  появился.
* `Clear*` дублирует `Ext*` — это не разные величины, отдельно их считать не
  нужно.
* `MaxItems` почти везде `0`, полагаться на него как на лимит нельзя.
* `Depth` есть только у `Type=drawer`; в остальных строках ячейка пустая, а не
  нулевая.
* `Loc*` на движке планируют вывести позже — **сейчас** они валидны и нужны.
  `Ext*` читать обязательно: из них строится коллайдер «вещь внутри».

## 8. Как проверить со своей стороны

```bash
blender --background --python-exit-code 1 --python verify_slots.py -- --baseline <снимок>
```

Что он гоняет: две модели (`bedside_dresser` — ящики без единой двери,
`full_l_kitchen` — двери, ящики и повёрнутые секции), каждая запекается
**дважды** (перезапекание обязано быть no-op по именам), вывозится в FBX и
**обратно импортируется в Blender**; сверяются имена сокетов против §4.2,
родитель-меш против типа строки (§4.3), позиция против `Loc*` — для `drawer`
как `монтаж × коллизия == Loc` — поворот против секции, неповторяемость
номеров, число сокетов по формуле из §6.

`--baseline` необязателен: без него бегут все проверки нового поведения, с ним
добавляется сравнение с прежним снимком. Сравнение — **не побайтовое**: имена
сокетов замаскированы, поэтому `_doors.csv`, `_drawers.txt` и mesh-секция
отчёта обязаны совпасть во всём, что не является именем сокета. Любое другое
изменение валит тест.

`_drawers.csv` снимку, которому он предшествует, не сверяется — в старом
снимке его нет. Взамен он проверяется структурно (`check_drawers_csv`:
заголовок, разрешение каждой строки `drawer`, совпадение `Depth`, отсутствие
сирот), а сравнение включится само, как только снимок обновят: шлюз смотрит
на наличие файла в снимке, а не на список того, что стоит проверять.
